# System Design Reference — Part 4: Open Questions Before Build

> Part of the full system-design reference. See `README.md` in this folder
> for the complete set of parts. These are product/design questions not yet
> resolved — unlike Part 1, which documents decisions already made.

~~1. **Follow-up depth**~~ — **Resolved.** `MAX_FOLLOWUP_DEPTH=1` by default (one follow-up per topic, then move on), configurable in `.env`. Chosen to keep an 8-question, 30-minute session bounded — unlimited follow-ups risk one weak answer consuming disproportionate session time at the expense of category coverage.
2. **Blank/"I don't know" answers** — should these be logged as `did_wrong` or as a neutral `not_attempted` classification? Recommendation carried into `03-final-architecture.md` §3.3: use a distinct `not_attempted` value — conflating "wrong" with "skipped" would muddy the summary and unfairly penalize the user for honesty about a knowledge gap versus a factually incorrect answer.
3. **Timer visibility** — ~~should the CLI show a live countdown, or hide remaining time to reduce exam anxiety?~~ **Resolved.** Live countdown, always visible during `IN_PROGRESS`. The pipeline (`../design.md` §7) already excludes LLM latency from the clock, so a live countdown reflects genuine remaining answer time rather than being misleading padding.
4. **`SESSION_RETENTION_DAYS` value** — ~~`05-repo-lifecycle-and-language-coverage.md` §5.4 establishes *that* SQLite/profile/Chroma data expires on a configurable window, but not the default number of days.~~ **Resolved.** Default `7`.
5. **`LLM_MODEL` selection for the classification call** — **resolved.** Pressure-tested 7 candidate models (`docs/system-design/07-llm-model-pressure-test-results.md`); `gemma4:e4b` is the new default, the only candidate that showed real signal on partial-correctness detection instead of defaulting to `correct`. `mistral-nemo:12b` was ruled out for reproducibly marking wrong answers `correct`. Manual Phase 0 exit-criteria testing (walking-skeleton `viva demo`, same fixed answer, repeated across runs) originally surfaced two distinct reliability concerns rather than one:
   - **Within-model inconsistency:** `qwen2.5-coder:7b` classified the *identical* answer as `partial` in one run and `incorrect` in another, with near-identical free-text reasoning in both — i.e. the constrained-decode `classification` field and the model's own explanation disagreed with each other within a single response, not just across responses.
   - **Between-model citation compliance:** on the same fixed answer, `qwen3.5:latest` reliably included a specific, on-target `cited_file` (down to a line range) for a `partial`/`incorrect` verdict, while `qwen2.5-coder:7b` omitted the citation in both observed runs — correctly triggering the FR22 `needs_review` downgrade (`../llm_client.py`), but at the cost of the verdict never reaching the user as a usable evaluation.
   - Schema validity itself was not the problem in any observed run — every response parsed as valid JSON on the first attempt across all Phase 0 testing. The risk is narrower than "small models can't do structured output": it's specifically *label/rationale self-consistency* and *citation-instruction compliance*, and it appears to vary by model even within the same rough size class.
   - **Recommendation:** before Phase 1 finalizes a default `LLM_MODEL`, run a small fixed pressure-test — the same 3-5 answers (a mix of correct/partial/incorrect/blank) against each candidate model (at least `qwen2.5-coder:7b` and `qwen3.5:latest`), N=4-5 repetitions per answer per model — and track classification stability and citation-compliance rate per model. This is cheap (the Phase 0 `evaluate_answer` call already does the work; it just needs to be run in a loop and logged) and turns an anecdotal n=1-2 observation into an actual selection criterion rather than a default picked without evidence.
